## The client fix (2026-10-15, MR !173)

The repro and fix live on the eqemu lane 2 x86/llvmpipe client, not on the
XU4: a scripted `/target` + `/moveto` + `/face` on Guard_Treitan (race 71,
multi-buffer model, qeynos2) rendered the "smear" with `--eqe1-path` (ETC1)
and correctly without it (raw RGBA), while single-buffer zone ETC1 rendered
correctly in both — see `STEP_A_x86_capability.md` for the full outcome
tables, the llvmpipe-accepts-ETC1 probe (`mesa-probe/etalib.c`), and the
WILLEQ_B1051_TRACE evidence. That clears the driver on both GPUs; the fault
is the client.

**Mechanism (measured, not inferred).** In an EQE1-authoritative run the
character S3D parses as "472 textures with 0 raw bytes", so the raw per-part
bytes are released at parse time (`RaceModelLoader::loadModelZone` →
`releaseBytesIfEqe1Authoritative`, `race_model_loader.cpp`). `ZoneMeshBuilder::getOrLoadTexture()` — the
on-demand per-buffer path `mesh_building.cpp` uses for multi-buffer
characters — consulted only its own `textureCache_`/`pendingTextures_` maps,
both empty, and returned nullptr; each buffer then fell to the textureless
diffuse fallback, the flat (255,200,180,160) body. The per-part GPU textures
DO exist — the Compressed-source ETC1 lookup (`ConstrainedTextureCache::
getOrLoad()` → `findCompressedEntry`) has queued them — but
`getTexture()` only sees PROMOTED entries, and the promotion (the actual
`glCompressedTexImage2D`, logged `ETC1 texture ... uploaded`) happens in the
render thread's upload loop. The timeline measured on lane 2:

| run | first race-71 guard mesh build (Step8c) | first per-part ETC1 upload | gap |
|---|---|---|---:|
| 912c (Guard_Drath, 2026-10-15 11:02) | 11:02:47.871 (first) / 11:02:47.885 (Drath's own) | 11:02:47.965 (`qcfch0001`) | 80-94 ms |
| continuation (Guard_Treitan, 2026-10-15 15:48) | 15:48:01.847 | 15:48:02.001 (`humch0001`) | 154 ms |

The single-buffer zone path (`buildTexturedMesh()`) survived because it is
built from already-promoted entries and already had the
`constrainedCache_->getTexture()` fallback — the on-demand path did not.

**Fix (two commits, MR !173).**
1. `bf2a8968` — `getOrLoadTexture()` (and `hasTexture()`) fall back to
   `constrainedCache_->getTexture()`, mirroring `buildTexturedMesh()`.
2. `ad7295e1` — the refinement: that alone still misses a queued-but-not-
   promoted entry (the 80-154 ms gap above), so the on-demand path promotes
   it synchronously via `constrainedCache_->uploadTexture()` — the same call
   the render thread's loop makes; the path already does driver GL work
   (`loadTextureFromBMP`), so no new thread/context assumption.

Pinned by `tests/test_b1051_mesh_texture_fallback.cpp` (3 tests, incl.
`QueuedEntryIsPromotedSynchronouslyByTheOnDemandPath`, red on the
`getTexture()`-only fix, green with the refinement).

**Live x86 after-verification (this continuation, lane 2, head 433a1c2e).**
Same recipe as the pre-fix runs (Guard_Treitan, qeynos2,
`/target` + `/moveto` + `/face`, UI hidden): ETC1 (`--eqe1-path`) now renders

Single-buffer zone ETC1 still renders correctly in the ETC1 run.

- **ETC1 leg** (`--eqe1-path /mnt/projects/EverQuest_ETC1`): Guard_Liben

  **loaded 0 variant textures** (`variants=0`). Still (frame_000155):

So the fix is **incomplete**: it does not restore per-NPC variant armour in

driver: the same binary's plain path loads the armour, the ETC1 path does not.

### Deeper root cause: variant QCM armour never enters the cache in ETC1 mode
Clean A/B over the whole leg (in-radius entities with `appearance.texture>0`
or `helm>0`), `ab_pairs.py`:

| leg | variant-armored | in-radius (seq) | of those loaded >0 variants |
|---|---:|---:|---:|
| RGBA | 42 | 42 | **42** (guards load 13) |
| ETC1 | 32 | 32 | **0** |

The ETC1 leg logs `RaceModelLoader::preloadVariantModel: merged texture cache
not valid, using global textures only` (variant_loading_preload.cpp:91). When
`mergedTexturesCacheValid_` is false, `preloadVariantModel` sources the variant
mesh's textures from `globalTextures_` only — which holds the **base** series
(`qcm*0001`, 13 qcm uploads + 7 qcf = 20 in the ETC1 leg,
`/home/user/b1051-after/fixed-etc1/client3.log`) but **not** the per-NPC
variant series (`qcm*0101/0201`, 0 uploads for the guard race; the only
`0101` uploads in that leg are non-guard races `betch*`/`betft*`/`bethe*`/
`betlg*`/`fishe*`). In the plain path the merged cache is built and valid, so
the variant series is present.

The variant series is **present in the ETC1 packs** (enumerated via the EQE1
index: `qeynos2_chr.eqe1` and `commons_chr.eqe1` each carry 51 `qcm*01xx/02xx`
entries incl. `qcmch0101`, `qcmfa0101` + their `_alpha` companions). So this is
**not an asset gap** — it is the ETC1/archive-index load path failing to build
the merged texture cache that `preloadVariantModel` falls back off. The base
`0001` textures load because they are global; the per-NPC `01xx` variants are
zone/chr-file textures that only reach the merge once the merged cache is
built, which never happens in ETC1 mode.

### The step-8c promote fix (separate, smaller, real)
A distinct defect: the sequential zone-load path staged each race model in
`preparedModelData_` (step 8a) but `getRaceModelData()` only reads the main
cache, and promotion ran once per entity *after* step 8c (loop bottom). The
first in-radius entity of each race/gender therefore saw `modelData=false`
and loaded 0 variants. Fixed by promoting in step 8c before the read
(`renderer_zone_load_entities.cpp`, commit 8ef0952d). The dynamic/deferred
path already promoted before reading (entity_mesh_build.cpp:154,
entity_build_step.cpp:273), which is why only the sequential first-of-race
entity was affected. This is a genuine but **separate** bug from the ETC1
variant-cache defect above; it alone does not close finding (a) (the ETC1 leg
still loads 0 variants for all 32 in-radius variant-armored entities even
with it).

### Left open
The ETC1-mode merged-texture-cache defect (variant `01xx` QCM armour never
reaches the cache under `--eqe1-path`) is the remaining client-side cause of
the flat ETC1 NPC render on x86 — and, if it reproduces on the device, of the
same class of flat render there. It is in the client path this MR touches
(constrained cache + zone/chr texture merge), but the fix is a
multi-site change to the ETC1/archive-index model-load path, out of scope for
a one-line patch. Direction for Will: either extend the ETC1 load path to build
the merged texture cache the plain path does (the client-side close), or treat
the x86 ETC1 flat render as this client defect and the Xu4 A/B as the driver
leg.
