# T213 — races 415 and 457 no longer render as placeholder cubes

Evidence: `review/T213/`. Closes the asset gap T211 explicitly left open.

## What they are
From the eqemu server's own header (`common/races.h`):

    constexpr uint16 Rat       = 415;
    constexpr uint16 Gnomework = 457;

Both postdate Titanium. Neither was in `config/race_models.json` (185 entries,
highest key 367), so `getRaceCode()` returned empty, no model could be found, and
`EntityRenderer` fell back to a con-coloured placeholder cube:

    Skipping entity 274 (a_rat000): base race model not found:
      race=415 gender=2 (not found in any S3D archive) — placeholder cube
    Skipping entity 267 (SummonClockworkBanker000): race=457 gender=2 — placeholder cube

## Is there a real Titanium model to point at?
Checked rather than assumed. `docs/reference/s3d_contents_reference.json` indexes
the whole client: 400 S3D files, 3548 models, **209 distinct model codes**.
Cross-referencing those against every code `race_models.json` already claims:

    codes in the client mapped to NO race: []   <- none spare

Every model the Titanium client ships is already claimed by some race, so there
is **no distinct model for 415 or 457 to find**. What does exist is the same
creature under its classic race id:

    race  36  "Rat"             code RAT  akanon_chr.s3d
    race  88  "Clockwork Gnome" code CLM  akanon_chr.s3d  (female CLF)

Race 415 *is* a rat; race 457 *is* a clockwork gnome. Pointing them at those
models is the correct Titanium representation, not a cosmetic bodge — and the
entries record that explicitly via `alias_of` / `alias_reason` so a later reader
does not mistake them for independent models.

## The change
`config/race_models.json` gains 415 (-> RAT, scale 0.3) and 457 (-> CLM/CLF,
scale 0.6), each with the `also_in` list of the race it aliases, and
`data/willeq.db` is rebuilt via `willeq_db_builder` (185 -> 187 race_models rows).
The runtime reads races from SQLite on demand, so the rebuilt DB is the part that
actually takes effect; the JSON is its source.

Gender needed no special handling: both NPCs arrive as `gender=2`, and
`getGenderedRaceCode()` returns the base code for anything other than gender 1.

## Verified
Forced both races on screen with GM commands (npc_types 999415 / 999457,
`#npctypespawn` in qeynos2):

    [NPC] id=196 'T_Rat000'       bspRegion=1161 inGraph=true placeholder=false
    [NPC] id=197 'T_Gnomework000' bspRegion=1161 inGraph=true placeholder=false

- `base race model not found` occurrences: **0** (both races previously logged it)
- Real geometry, not a stand-in shape:
  `preloadVariantModel: race=415 (RAT) variant (head=1, body=0) loaded (904 verts, 9 anims)`
  and `preload race=457 gender=2 took 2ms success=true`
- `akanon_chr` — not a qeynos2 zone archive — was opened and served 14 lookups,
  because T199's spawn-driven archive selection queued it *from these new
  mappings*. The whole chain works end to end.
- Full-frame magenta scan: 0 pixels.

Suite 2745/2746 (sole failure the known ALSA host quirk). Test npc_types removed.

## Honest limits
- **No clean portrait.** `#npctypespawn` always drops the NPC at the invoker's
  position, and `#zone`'s coordinate arguments are ignored in favour of the zone
  safe point, so every spawn landed on the crowded zone-in spot with five models
  interpenetrating. The captures in `review/T213/` show the models rendering but
  are not a usable identity shot. The log evidence above (vertex/animation counts
  from the named RAT model, `placeholder=false`) is the stronger proof and is what
  this unit rests on.
- **Side observation, not fixed here:** the T207 usage report shows `qeynos2_chr`
  serving 0 lookups on one zone load. Zone archives ({zone}, {zone}_obj,
  {zone}_chr) are still opened *eagerly* at Step 0 — T207 only removed the
  speculative opening of the *global* list. Worth a look, but it is a different
  defect from this one.
