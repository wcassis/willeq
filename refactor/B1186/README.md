# B1186 (#505): the landing_cov window — like with like

**Verdict.** The window mismatch is REAL on the tour and absent on b1130.

- **Tour (b1118 rig):** the willeq side normalizes its landing lit px by the
  b1118 rig's OWN rendered-caster height, **235 px**, while the B1178 v3 oracle
  reference was normalized by the ORACLE capture's own measured-caster height,
  **214 px** (sec. 1). Record 80 / spell 93, from ONE willeq render on this
  tree: the same peak (168,923 lit px at Act+1.93 s) reads **3.059 (0.683×)**
  at 235² and **3.689 (0.824×)** at 214², against the oracle's 4.479
  (sec. 2) — the domain difference the issue asked to prove.
- **B1130:** BOTH committed sides are already at **209²** — the oracle
  capture's own caster height, read from the SAME geom files on both sides
  (sec. 1). The unification is a verified no-op and the 38/40 red rows are the
  measured same-window pixel gap (0.55× at the B1166 measure), owned by the
  B1164/B1172/B1180 sprite-size chain — NOT a window domain (sec. 5).

Will's rule, applied: the window on both sides is the capture's own measured
height, never a fitted proxy. The reference is BLESS-ONLY, so the side that
moves is the willeq one — re-derived at the oracle capture's own per-row
window from the SAME measured frames. No harness value tuned, no reference
changed, no golden touched.

## 1. How the landing window is derived, both sides, with lines

Landing coverage on both sides is one quantity: the count of lit pixels
(`(frame − baseline).max(channel) > 80`) inside a fixed crop, at the peak
frame of the landing run, divided by a figure's height, **squared**. The only
degrees of freedom are the crop, the peak-run rule and the divisor.

**Tour — willeq side (b1118 rig).** Crop `170,0,1060,650`
(`review/B1139/scripts/harness_measure.py:43`); the lit series is `lit80.tsv`
per spell; the gate column `land_cov`
(`review/B1132/scripts/b1123_summary.py:3`: the peak of fx_timing's
tail-baseline lit series over Act+1.0 s .. the end, computed at
`review/B1132/scripts/b1123_summary.py:28-29`), divided by
`MPX = 235.0` (`review/B1132/scripts/b1123_summary.py:15`), emitted at
`review/B1132/scripts/b1123_summary.py:49`. The 235 is the
b1118 rig's own rendered-caster height — "the B1118 tour's own numbers are
row 605 / 235 px" (`tools/model_viewer/model_viewer_fx_harness.cpp:824`,
the rig's default `casterPx = 235.0f`,
`tools/model_viewer/model_viewer_fx_harness.h:74`) — a height the rig SOLVES
for (the camera distance is iterated until the rendered caster silhouette
measures exactly that; `tools/model_viewer/model_viewer_fx_harness.cpp:138`),
i.e. a fitted figure, not the oracle's.

**Tour — oracle side (B1178 v3).** Crop `150,60,900,540`
(`review/B1178/worker/measure_leg.sh:24`); the LANDING line's coverage is
`lit[peak] / mpx²` with the model passed in (`review/B1132/scripts/fx_timing.py:54`);
`MODEL=${3:-214}` (`review/B1178/worker/measure_leg.sh:8`, invoked at
`review/B1178/worker/measure_leg.sh:25`), the 214 measured off the oracle's
OWN stills at the pinned camera — "model 214 px: head row 388 ... feet 602"
(`review/B1178/worker/measure_leg.sh:5`; `refactor/B1178/README.md:175`), and every
per-record leg's timing file prints "model 214px" with its LANDING coverage
(`refactor/B1178/README.md:184`). The committed oracle values live in
`tests/spell_fx_population_oracle.h:81-88 (kTour)` (spell 93: 4.479).

**B1130 — willeq side.** The instrument is per KIND, not per record: crop
`150,60,990,540` (fixed_npc) / `150,60,900,540` (fixed_self), `mpx = 209.0`
on BOTH kinds — the GEOM dict at `refactor/B1155/scripts/harness_measure_b1130.py:49-53`,
whose comment names the provenance ("review/B1130/geom/r51.json (every
fixed_npc cast; target anchor above), review/B1130/geom/r131.json
(fixed_self)"). The gate column `landing_cov` is the RISE coverage — the
tail-baseline lit series, full crop, peak of the rise run, divided by
`mpx²` (`review/B1132/scripts/landing_onset_abs.py:44`), invoked with the
geom mpx at `refactor/B1155/scripts/harness_measure_b1130.py:99`.

**B1130 — oracle side.** The same files and the same instrument:
`review/B1130/scripts/process_record.sh:21-23` (fixed_self crop
`150,60,900,540` mpx 209; fixed_npc crop `150,60,990,540` mpx 209), read by
`review/B1130/scripts/cast_measure.py:52` (landing_onset_abs with the geom
mpx). The committed reference is `oracle_landing_cov` in
`refactor/B1153/tables/gate_c.tsv` (regenerated by B1178).

So: **tour = 235² (willeq, fitted rig) vs 214² (oracle, its own stills) — a
real window domain; b1130 = 209² vs 209² — already the capture's own, on
both sides.** The target's measured height (288 px, the B1166/B1178 anchor

p90_land ROI (`refactor/B1155/scripts/harness_measure_b1130.py:77`,

## 5. Why the b1130 rows are not a window domain — correcting the attribution

The issue carries the attribution B1184 states: "The residual is the
measurement domain: the harness window is per-target-height^2 (the
anchor-fitted target's height), the oracle reference the oracle target's
height" (`refactor/B1184/README.md:135-138`). Checked against the
committed instruments, that wording names the wrong divisor, on all four
sides:

1. **The committed b1130 `landing_cov` divides by 209² on both sides** — the
   oracle capture's own caster height (sec. 1: the willeq GEOM dict
   `refactor/B1155/scripts/harness_measure_b1130.py:49-53` and the oracle
   geom files `review/B1130/geom/r51.json` / `r131.json`, both `mpx: 209`,
   read by `review/B1130/scripts/cast_measure.py:52`). The window is already
   the capture's own, on both sides; unifying it is a verified no-op.
2. **The target's measured height (288 px,
   `tools/model_viewer/fx_target_anchor.h:44`) is not a divisor anywhere in
   `landing_cov`** — it enters only the LANDING anatomy (p90_land ROI and
   the anchor call, `refactor/B1155/scripts/harness_measure_b1130.py:77`,
   `:80-81`, `:101`), where BOTH sides already agree (B1178 re-measured the
   oracle's anatomy at the same 288/615/940 anchor).
3. **"per-target-height²" names B1164's diagnostic instrument, not the gate:**
   `b1164_regions.py`'s peak window is "target heights^2"
   (`refactor/B1166/README.md:339`), and B1166's verdict on it is explicit —
   "the landing's lit pixels are 80960 / 147318 = 0.55x the oracle's in the
   same pixel window (0.80x if normalised by each side's own target height).
   The sim is not exonerated by the window measure; this joins B1164's (#483)
   pixel-area gap" (`refactor/B1166/README.md:351-353`).
4. **B1171's OWN attribution for the 38-row red was pixel area, not window:**
   "landing_cov short (38 rows): B1164 (#483), the landing's pixel area ...
   the shortfall is not the target body: a fixed_self landing is on the
   caster, whose height is fitted"
   (`refactor/B1171/README.md:124-128`). The "fitted height" phrase there is
   the BODY term (the lit pixels of the landing host), which B1171 rules out
   as the shortfall — not a claim about the `landing_cov` divisor.

So the b1130 reds keep their B1164 (#483) area / attach-scale owner (B1172
#491 and B1180 #500 loaded: `refactor/B1180/README.md:206`,
`refactor/B1171/README.md:214`), now measured at the unified (already-own)
window in sec. 4. The TOUR rows DO carry a window component — the CASTER's
height, fitted (235, the rig's solved silhouette) on the willeq side vs the
oracle's own still (214), not the target's (sec. 1, sec. 2) — which is what
B1184 named for the tour: "the tour landings all sit short of the B1178 v3
references (the same window domain — the tour's land_cov is the same
per-target-height^2 window metric, just on the pinned b1118 rig)"
(`refactor/B1184/README.md:237-239`).
