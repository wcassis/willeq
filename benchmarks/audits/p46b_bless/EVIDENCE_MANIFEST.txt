P46b — Wrong-texture regression in P46's bless pairs: root cause, fix, retake
====================================================================

Purpose: Will REJECTED P46's bless pair (round 3): "BEFORE looks correct,
AFTER has the wrong texture for some skeleton body parts and some zombie
body parts" (orange/saturated skeleton forearms+shins, glowing-amber zombie
chest, partly-cut-away zombie skirt). This unit bisects the regression to a
specific commit/file/line, root-causes the mechanism, fixes it, and retakes
the bless pairs from the fixed tip. P46's own evidence is superseded by this
manifest (see refactor/P46_masked_alpha_decode.md Review annotation).

Part B: Root cause
-------------------
File: `tools/hwcaps/zone_bench_loader.cpp`, `applyEntityAlphaCompanionBinding()`
(P46 commit d19e325, originally lines 56-92).

Production's `EntityRenderer` (`src/client/graphics/entity_renderer.cpp`,
e.g. the loop at lines 629-648) promotes an entity's material buffers in a
single PAIRED step at each of its 3 material-assignment call sites:
```
if (mat.MaterialType == EMT_SOLID) {
    mat.MaterialType = shaderMaterialSolid_;       // custom per-pixel-lit shader
} else if (mat.MaterialType == EMT_TRANSPARENT_ALPHA_CHANNEL_REF) {
    applyAlphaTestMaterialType(mat);               // custom alpha-test shader
}
mat.Lighting = false;  // shader handles lighting
```
Both halves fire together, so EVERY buffer on an entity -- masked or not --
ends up on the SAME custom GLSL lighting shader family (real per-pixel
player light, sun, fog, tint -- see `zone_shader.cpp`'s
`FRAGMENT_SHADER_SOLID_SRC`/`FRAGMENT_SHADER_ALPHA_SRC_BASE`/
`FRAGMENT_SHADER_ALPHA_RGBA_SRC`, which compute IDENTICAL lighting math,
differing only in the alpha-discard test).

P46 Part B ported ONLY the alpha-test half of this pair (mirroring
`applyAlphaTestMaterialType()`) into the benchmark's `--animate` entity path.
It never implemented the sibling `EMT_SOLID -> shaderMaterialSolid_`
promotion. `mesh_building.cpp` assigns every entity buffer either
`EMT_SOLID` (unmasked) or `EMT_TRANSPARENT_ALPHA_CHANNEL_REF` (masked, P37).
With only the alpha half ported: masked buffers (skeleton forearms/shins =
skeft0001/skeft0002/skelg0001; zombie chest/legs = zomch0001/zomlg0001 --
exactly P37's ground-truth masked list) got promoted to the custom
per-pixel-lit shader, while sibling unmasked buffers on the SAME entity mesh
stayed on Irrlicht's built-in fixed-function `EMT_SOLID` renderer (flat
vertex-color modulate, no player light/sun/fog contribution). Every masked
body part rendered through a visibly different lighting model than its
unmasked neighbors -- independent of any real per-pixel alpha value, which
is exactly what the bisect matrix's "Part A revert changes nothing" finding
proves. This produced precisely the reported symptom: masked parts render
warm/saturated/"glowing" against their unmasked siblings' flatter, cooler
fixed-function look. Not a texture-identity bug (wrong bitmap, wrong part
mapping) at all -- a shader-consistency bug from an incomplete production
mirror, confined to this benchmark tool (production's entity_renderer.cpp
has paired these two promotions since before P37 existed).

Fix (this unit, commit -- see git log)
-----------------------------------------
`tools/hwcaps/zone_bench_loader.cpp`: renamed/restructured
`applyEntityAlphaCompanionBinding()` to `applyEntityShaderMaterialPromotion()`,
now iterating ALL of an entity's mesh buffers and applying the SAME paired
promotion entity_renderer.cpp does: `EMT_SOLID` buffers get
`shaderMaterialSolid` (a new parameter, `ZoneShaderManager::getActiveSolid()`
-- already used for zone geometry at this file's line 323, just never wired
to entities), masked buffers get the existing alpha-test promotion
(unchanged logic), and `mat.Lighting = false` is set on every promoted
buffer, mirroring entity_renderer.cpp exactly. Call site (~line 787) updated
to pass `getActiveSolid()` alongside the existing alpha-test material types.
Benchmark-only change; no production source touched (production's
entity_renderer.cpp already did this correctly).

Proof
-----
1. **Per-part texture-name assignment unaffected**: this bug was never about
   texture identity/mapping (hypotheses 1/2/3 all exonerated by the bisect
   matrix's "Part A revert changes nothing" result -- Part A/race_model_loader.cpp/
   ConstrainedTextureCache are untouched by this fix). No texture-name log
   needed; the mechanism is a material/shader promotion gap, proven by the
   paired-vs-unpaired code diff itself plus the visual before/after below.
2. **Visual, part-by-part** (see stills below): BEFORE the fix (rejected P46
   state), skeleton forearms/shins and zombie chest render distinctly
   brighter/warmer than the torso/skull/thighs on the SAME entity --
   confirmed by side-by-side crop inspection. AFTER the fix, every body part
   on a given entity renders through the SAME lighting model -- uniformly
   warm/golden-toned (befallen's own established color grading; a
   zone-geometry-only crop with no entities, unaffected by this fix, shows
   the identical warm stone/pillar tones -- this is befallen's real ambient
   lighting, not an artifact). No patchwork, no part-specific saturation
   spike, no "wrong texture" appearance on either race in either leg.
3. **Rib-gap cutout**: skeleton ribcage renders with the same visible
   inter-rib gap detail as BEFORE at this camera framing (P44b's own finding
   that this specific angle doesn't show clean see-through-to-background
   holes still applies -- the numeric AE evidence, not this angle's pixels,
   is what demonstrates the alpha-test discard is real and engaged, per
   P46's own established evidence standard).
4. **Unmasked races (Human) -- REQUIRED DEVIATION, explained**: P46's plan
   required unmasked races to stay byte-identical to pre-P46. Under this
   fix, Human (race 1, no masked textures) now ALSO differs from fda2e34
   (AE=9184 @ f26) -- because the fix's whole point is applying shader
   promotion UNIFORMLY across every entity buffer, masked or not, matching
   what production has always done for solid buffers. This is not a
   texture-identity regression: a 400% crop of Human before/after (this
   session's scratchpad, not committed -- reproducible via the command
   above with --test-races 1) shows perfectly uniform, consistent lighting
   across face/arms/torso/legs in both states -- just a different (correct,
   shader-lit, production-matching) lighting model in AFTER, applied evenly.
   This widens P46's original narrow "masked-only" gating claim into the
   necessarily-correct "every entity, uniformly" gating claim; flagged
   explicitly rather than silently narrowed back to pass the original
   (now-inapplicable) invariant.

Deviations
----------
1. Unmasked-race byte-identity (P46's original gating requirement) legitimately
   no longer holds -- see "Proof" item 4 above. Necessary consequence of the
   fix, not scope creep: a partial (masked-only) promotion was THE BUG.
2. The bisect matrix's HARD STOP check has a documented instrument
   limitation (5420886 predates the benchmark's entity_renderer-equivalent
   linkage entirely) -- see "Part A" finding 1. Did not change the verdict
   (the plan's literal condition did not trigger) but is flagged rather than
   silently treated as a clean bill for pre-P37 production code.
3. Mid-session, an interrupted `scripts/build-gles2-x86.sh` invocation (killed
   partway through its `rm -rf`/re-copy of the pristine Irrlicht source, used
   to unblock a stuck background build) left the shared
   `third_party/irrlicht-gles2-x86/` tree in a half-wiped, non-functional
   state (missing `EDT_OGLES2` and the GLES2 driver sources). Caught
   immediately by the next build's compile errors; restored via
   `scripts/build-gles2-x86.sh --irrlicht-only` (deterministic, same patch
   script every prior unit in this codebase has relied on) before any
   further verification. `build-preP37/`, the main `build/` tree's already-
   linked binaries, and the 3 bisect-matrix scratch worktrees were built
   BEFORE the incident and are unaffected (static linking; only the shared
   header/source tree was transiently damaged, not already-produced
   binaries). All post-incident verification steps (ctest, visual gate, ARM
   build, file-size check) were re-run against the restored tree and pass.
   No repo-tracked files were touched (`third_party/irrlicht-gles2-x86/` is
   gitignored, generated).
