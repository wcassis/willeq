audits/* unit has committed PNG stills either — see e.g.
benchmarks/audits/p17_eviction_hygiene/, text/log evidence only). Following
that same convention, all P20 still screenshots live on NFS at

Deviation 1 in the plan Review for why orangepi_p20 vs. stock orangepi).

P20b — wind-shader MaterialType clobber fix (completes Part A)
----------------------------------------------------------------
Fixes the true live-client root cause named in P20's correction block:
renderer_zone_stream.cpp:559-576 and renderer_zone_load.cpp:2288-2334
unconditionally overwrote tree MaterialType with no masked/ETC1-vs-RGBA
classification. Fix applies H02d Option-A classification at both sites
(mirroring ZoneMeshBuilder::buildTexturedMesh) and adds wind-family shader
variants (materialWindAlphaTestRGBA_, materialWindSolid_ + lightweight
counterparts) in zone_shader.{h,cpp} so masked+RGBA and non-masked tree
materials no longer land on the ETC1-companion variant with an unbound
unit 1.

Same-pose before/after pairs, both captured live against eqemu
(scripts/eqemu/up.sh/down.sh), willeq --script tour files (identical
/turn or /move + wait sequences between BEFORE/AFTER runs, screenshot
filenames differing only in the _BEFORE/_AFTER suffix), stills at
/mnt/projects/fable/videos/p20_live_visual/stills/ (p20b_ prefix):

- gfaydark (nekpine ground-truth case): p20b_gfay_00/01/02/03_BEFORE.png
  vs. p20b_gfay_00/01/02/03_AFTER.png. Tour: data/captures/*.txt
  scratch (gitignored, contents reproduced in the plan's Review) —
  `#zone gfaydark` -> `#time 12` -> `/move 10 20 0` -> `/move 10 60 0`
  -> `/move 0 100 0`, screenshot after each move. BEFORE frames (_02,
  _03) show the large center pine's canopy as a solid, hard-edged,
  opaque dark-green rectangular panel blocking the sky, matching Will's
  original report. AFTER frames (_01, _02) show the same pine canopy
  rendering as a proper needle-shaped silhouette with sky visible
  through the negative space — same camera pose, only the foliage
  material changed.
- qeynos2 (gates trees, Will's original complaint scene): p20b_qeynos2_
  00/01/02_BEFORE.png vs. p20b_qeynos2_00/01/02_AFTER.png. Tour:
  `#zone qeynos2` -> `#time 12` -> `/turn 180` -> `/turn 165` ->
  `/turn 195`, screenshot after each turn (turn-only, no /move, so
  same-pose-by-construction is trivial — identical starting position,
  identical heading sequence). BEFORE frames show a pine (right of the
  willow) as a solid opaque rectangular panel. AFTER frames show the

P21 — door/entity masked-RGBA alpha gap (setShaderMaterialTypes 2->3 arg)
----------------------------------------------------------------
Extends door_manager.h/.cpp and entity_renderer.h/.cpp
setShaderMaterialTypes() from 2 to 3 args (mirroring
DoorManager/AnimatedTreeManager/ZoneMeshBuilder's existing 3-arg
signature), carrying the H02d Option-A RGBA alpha-test shader variant.
Same bug class as P20b (trees): masked RGBA-decoded textures previously
had no route to the RGBA-aware shader for doors/entities.

Ground truth (real vs latent, per-territory):
- DOORS — REAL, confirmed live. WLD ground truth: PAWHOOK_DMSPRITEDEF
  (qeynos2_obj.wld and befallen_obj.wld) is Fragment 0x30
  TransparentMasked, texIdx=0 pchain.bmp. Live DB ground truth: the
  qeynos2 `doors` table has 6 real placed PAWHOOK door instances (ids
  42,43,44,57,58,59 / DB ids 5972-5985), opentype=58, size=100 — not a
  decorative-only WLD object, an actual server-placed door. Live client
  run (build-gles2/bin/willeq, no --eqe1-path so the RGBA/DDS decode
  path is exercised) confirms: `pchain.bmp` decoded via the direct
  `[CONSTRAINED] texture 'pchain.bmp' decoded/uploaded` path (never the
  ETC1 path — no matching "ETC1 texture 'pchain'" log line anywhere in
  the run), and `ZoneShaderManager: RGBA alpha-test shader compiled
  (alphaTestRGBA=258)`.
- ENTITIES — LATENT-only, code evidence. WLD ground truth: multiple
  masked character-archive textures exist (e.g. befallen_chr.wld
  zomch0001.bmp/zomlg0001.bmp, qeynos2_chr.wld beahe0008.bmp, etc. —
  grepped via a throwaway WldLoader-based tool, not committed). BUT: a
  full audit of `MaterialType = ` assignments across
  src/client/graphics/eq/*.cpp shows only zone_geometry.cpp
  (ZoneMeshBuilder) ever assigns `EMT_TRANSPARENT_ALPHA_CHANNEL_REF`;
  the character/equipment mesh-build paths (mesh_building.cpp,
  equipment_model_loader.cpp — RaceModelLoader, outside this unit's
  territory) unconditionally hardcode `EMT_SOLID` regardless of the WLD
  masked flag. entity_renderer.cpp's classification extension
  (`applyAlphaTestMaterialType`) is therefore currently unreachable on
  the live non-composite entity path — masked entity textures never
  reach alpha-test at all today, a separate, larger, out-of-territory
  gap (RaceModelLoader ignoring textureMasked()). The fix is
  latent-correctness: it corrects the RGBA-vs-ETC1 selection for
  whichever future/composite path does reach that branch, matching the
  same bug-class pattern P20b used for trees, verified by full build +
  test suite passing.

Before/after code-level evidence (doors, PAWHOOK, qeynos2 — same-pose
live capture at `#goto -352 184 3`, identical `--script` file, identical
wait timings between runs; screenshots at
/mnt/projects/fable/videos/p20_live_visual/stills/
p21_qeynos2_pawhook_00_BEFORE.png / _AFTER.png). A temporary,
uncommitted diagnostic (reverted before the final build/commit, same
pattern as P20b's own uncommitted evidence workarounds) traced the
`MaterialType` actually applied to the PAWHOOK door mesh buffer at build
time:
- BEFORE (door_manager forced to drop the RGBA arg, reproducing pre-fix
  2-arg behavior): `P21_EVIDENCE door='PAWHOOK' buf0.MaterialType=14`
  — Irrlicht's `EMT_TRANSPARENT_ALPHA_CHANNEL_REF` (fixed-function),
  which the GLES2 driver's all-shader pipeline (6 compiled programs,
  see src/client/graphics/CLAUDE.md) does not implement.
- AFTER (fix restored): `P21_EVIDENCE door='PAWHOOK'
  buf0.MaterialType=258` — the compiled GLES2 RGBA alpha-test shader
  (`alphaTestRGBA=258`), which reads `uTexture.a` directly.
This numeric MaterialType trace is the decisive evidence for this unit:
the PAWHOOK door mesh itself is small and not visually prominent at the
`-352,184,3` establishing-shot vantage used (same wall/willow/pine scene
P20b's own qeynos2 evidence used) — the BEFORE/AFTER stills are
same-pose-by-construction but do not show an obvious visual delta on the
door object itself, honestly noted rather than overclaimed. The
MaterialType 14->258 transition is unambiguous, deterministic, and
directly tied to the exact real WLD/DB-confirmed masked door texture.
