ROOT CAUSE of the pixel-level null (why "verified taking the alpha-test
path" does not equal "visibly different pixels")
---------------------------------------------------------------------------------
mesh_building.cpp's fix only sets `buffer->Material.MaterialType` and binds
the MAIN texture on unit 0 (`setTexture(0, texture)`) -- it does NOT bind a
companion alpha texture on unit 1. In production, that companion-binding
(ETC1-masked -> unit-1 companion / RGBA-masked -> direct-alpha shader
variant) is done exclusively by `EntityRenderer::applyAlphaTestMaterialType()`
in entity_renderer.cpp (P21's plumbing, P37's Review explicitly names this
as the consumer of its MaterialType marker). `entity_renderer.cpp` is NOT
compiled into gles2_zone_benchmark (confirmed: `nm -C build/bin/
gles2_zone_benchmark | grep applyAlphaTestMaterialType` -> no match, and the
tool's CMake source list has no entity_renderer.cpp). Without
applyAlphaTestMaterialType(), the entity mesh buffer keeps Irrlicht's
built-in `EMT_TRANSPARENT_ALPHA_CHANNEL_REF` material type, which the GLES2
driver (`COpenGLES2Driver::applyMaterialState`, docker/irrlicht-drm/
COpenGLES2Driver.cpp) maps to the built-in `EOGLES2SP_ALPHA3D` shader
program -- and that shader (`ALPHA3D_FS_BASE`/`_DERIVATIVES`,
COGLES2Shaders.cpp) reads its discard alpha from `texture2D(uTexture,
vTexCoord).a` on unit 0 ONLY. For ETC1-loaded textures (--eqe1-path), unit 0
is an ETC1_RGB-compressed texture with NO alpha plane at all (opaque
format) -- alpha always reads 1.0, so the discard never fires, regardless
of camera distance or angle. Re-ran without --eqe1-path (forcing raw BMP
decode instead) to test whether the BMP's own alpha/color-key data would
work through unit 0 directly -- still 0 pixel difference at all 3 angles,
meaning the raw BMP decode path also does not deliver a real alpha channel
that this generic shader can discard on for these textures. This is a real
gap in gles2_zone_benchmark's entity rendering fidelity relative to
production, not evidence against P37's fix -- P37's fix demonstrably DOES
change what production's entity_renderer.cpp receives (mesh_building.cpp's
correct MaterialType marker, confirmed above), it is simply not visually
exercised by this offline tool.

P44c ADDENDUM -- RGBA leg (no --eqe1-path), same slot/branch, same day
================================================================================

Purpose: P44b's own manifest already noted "Re-ran without --eqe1-path
(forcing raw BMP decode instead) ... still 0 pixel difference," offered
without a decode-level root cause. This addendum's job: root-cause that null
one level deeper, per the standing instruction ("if RGBA ALSO comes back
pixel-identical: root-cause one level -- alpha lost at decode? material
assignment not reaching shader selection? -- and stop").

Hypothesis (from entity_renderer.cpp's own comment,
applyAlphaTestMaterialType(), ~line 219): "The direct RGBA/DDS decode path
has real alpha in the main texture's own alpha channel ... the RGBA variant
reads uTexture.a directly instead [of a companion texture]." If true, the
RGBA/no-eqe1-path leg should not need entity_renderer.cpp's companion-
binding at all -- the built-in EOGLES2SP_ALPHA3D shader (unit-0-alpha-only,
per P44b's root cause above) should just work on its own, sidestepping
P44b's tool-linking gap entirely.

FINDING: the hypothesis's premise does not hold for THIS codebase's RGBA
decode path. Alpha is lost one step earlier than the shader/material layer
-- at BMP decode.

`ConstrainedTextureCache::decodeBMP()`
(src/client/graphics/constrained_texture_cache.cpp, ~line 1151), which is
what BOTH gles2_zone_benchmark's --eqe1-path-less entity path AND
production willeq's entity texture loading (RaceModelLoader ->
ZoneMeshBuilder::loadTextureFromBMP -> ConstrainedTextureCache::getOrLoad
-> processTextureData -> decodeBMP, whenever no --eqe1-path/ETC1 pack is
configured) both funnel through, handles 8bpp paletted BMPs (confirmed via
a temporary trace -- see below -- that every ground-truth masked SKE
texture is 8bpp) by hardcoding alpha=255 for every pixel. The code's own
comment at the 8bpp branch says it plainly: "// A (ignore palette alpha)".

Contrast with tools/eqe1_builder.cpp's BMP decoder (~line 88), which
DOES implement EQ's actual masking convention for the offline ETC1
pipeline: "EQ convention: palette index 0 is the transparent color. Pixels
referencing index 0 get alpha=0, all others get alpha=255." This logic
exists exactly once in the codebase, in the eqe1 pack builder -- it was
never ported to ConstrainedTextureCache::decodeBMP(), the runtime decoder
used by the direct-BMP/RGBA path.

Diagnostic method (temporary, reverted before final build/commit, same
idiom as P44b's own): two single-line fprintf(stderr, ...) calls, one in
ConstrainedTextureCache::getOrLoad() right after processTextureData()
returns (prints texture name + hasAlpha + dimensions), one in decodeBMP()
right after reading bitsPerPixel (prints bpp). Ran
`./build/bin/gles2_zone_benchmark --zone befallen --eq-path
/mnt/projects/EverQuestP1999 --entities 1 --test-races 21 --orbit-radius 8
--orbit-height-offset 6 --animate --frames 3 --warmup 0 --dump-frames 1`
(no --eqe1-path). Trace (ground-truth masked SKE textures only):

  skefa0001.bmp hasAlpha=0 w=32 h=64   (bpp=8)
  skeft0001.bmp hasAlpha=0 w=32 h=64   (bpp=8)
  skeft0002.bmp hasAlpha=0 w=32 h=64   (bpp=8)
  skech0001.bmp hasAlpha=0 w=128 h=128 (bpp=8)
  skelg0001.bmp hasAlpha=0 w=32 h=32   (bpp=8)

Every one of P37's ground-truth masked textures decodes with hasAlpha=0 on
this path -- confirming the discard shader (unit-0-alpha-only, per P44b's
root cause) can never fire here regardless of MaterialType classification,
tool linking, camera framing, or anything downstream of decode. Reverted
both diagnostics (`git checkout -- src/client/graphics/
constrained_texture_cache.cpp`) before the confirmatory render below;

Verdict: RGBA leg is ALSO a full null, but for a DIFFERENT and more
consequential reason than P44b's ETC1/entity_renderer-linking gap. P44b's
gap is a benchmark-tool-only fidelity issue (production willeq DOES link
entity_renderer.cpp). This addendum's gap is NOT benchmark-only:
ConstrainedTextureCache::decodeBMP() is the same decoder production willeq
uses for entity textures whenever no --eqe1-path/ETC1 pack is configured --
so the RGBA/direct-BMP masked-texture visual effect cannot be demonstrated
in ANY tool, including a live production client, until decodeBMP() gets
the same palette-index-0-transparent logic eqe1_builder.cpp already has.
Per the standing instruction ("lead with this if RGBA also comes back
null"): the tool-fix unit remains the only path to visual bless evidence,
and this decodeBMP() gap is now a SECOND, arguably higher-priority
candidate for it (P44b's entity_renderer-linking fix only helps the
offline benchmark; this decodeBMP() fix would matter for real RGBA-mode
rendering, not just the benchmark).

visual-proxy path for the cutout SHAPE (mask is binary, geometry/UVs
identical to the ETC1 companion-texture mask) precisely because the live

finding above, that proxy claim is currently moot: the RGBA path cannot
