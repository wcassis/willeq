P08d: composite entities vs multi-buffer — RETAKE, aligned evidence

This replaces the original P08d evidence. The original contact sheet (0.4-2.3% differing pixels claimed at f10/30/50) was measured using gles2_zone_benchmark --composite-entities, which routes composite entities through renderCompositeEntities() — a P08c-era manual-draw stand-in with its own frustum-cull test (frustumCuller->testSphere), separate from the default entity path's cull test that the baseline (and production's EntityRenderer) actually use. That mismatch, not any defect in the real composite mesh-building code, caused the two runs to show different entities at different apparent positions at the same simulated frame — up to 38,728 differing pixels at one frame, including the "arm-only" frame Will flagged. Root-cause analysis (below) confirmed animation clip/progress were byte-identical between runs at every frame in every case — the divergence was 100% a render-dispatch artifact of this benchmark tool, not a production bug in the composite path itself. A new --composite-scenegraph flag was added to gles2_zone_benchmark (loads the real production composite mesh via RaceModelLoader::setCompositeEntityPath/preloadModelData, exactly as before, but renders through the SAME default entity draw path as baseline) to produce this corrected evidence.

Root cause (summary — full writeup in the plan's Review)

  1. Not animation-clip divergence. A temporary diagnostic (removed before commit) logged the selected animation code and playback progress for every entity, every frame, in both the baseline and the (broken) --composite-entities run: 0 differences, always. This directly refutes the "clip selection differs" hypothesis.
  2. Not vertex/mesh corruption in the real composite path either (though a real, separate, minor issue WAS found — see below). World-space bounding boxes of the rendered composite meshes were normal/tight at every frame checked (no exploded or displaced geometry).
  3. The actual cause: renderCompositeEntities()'s custom frustum-cull test disagreed with the default entity path's cull test for entities near the frustum boundary, so a DIFFERENT subset of the 6 placed entities ended up visible (and at different apparent sizes/positions) between the two runs at the same simulated frame — a benchmark-harness bug, not a production one. Fixed via --composite-scenegraph, which keeps the real composite-mesh loading but renders through the default (non-custom) entity path.

Aligned comparison (default orbit, qeynos2, 6 entities, --animate, seed 42)

Both runs use the SAME procedurally-generated camera path (deterministic from zone+seed, confirmed identical in log output) and the SAME entity placement. Baseline = default entity path (multi-buffer). Composite = --composite-scenegraph (real production composite mesh, same draw path as baseline).

Close-up (orbit-radius 15 — camera passes close to an entity)

The default orbit never brings the camera close enough to any entity for a full-frame close-up (per Will's earlier "arm shot" feedback) — the orbit-fallback camera's radius is fixed by zone geometry, not entity position. Using --orbit-radius 15 (still deterministic, same flag on both runs) brings frame 30's nearest entity into a proper close-up.
